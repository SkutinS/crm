# CRM

Лёгкая CRM для сервисного бизнеса: клиенты, задачи по клиентам с этапами,
учёт работ/запчастей/расходов/доходов/зарплаты и расчёт прибыли по задаче,
календарь запланированных работ, иерархические справочники услуг и
запчастей, настройки (тема оформления, валюта учёта).

## Стек

- **Backend**: Python 3.11+ / FastAPI / SQLAlchemy 2 / Alembic. Авторизация —
  логин/пароль, JWT (`python-jose`), пароли хешируются `bcrypt`.
- **БД**: SQLite для локальной разработки (файл `backend/crm.db`).
  Переключение на PostgreSQL — это только смена `DATABASE_URL` в `.env`
  (например, `postgresql+psycopg://user:pass@host:5432/crm`) плюс
  `pip install psycopg[binary]`; миграции Alembic и код приложения трогать
  не нужно.
- **Frontend**: React + TypeScript (Vite), UI-библиотека Mantine 7,
  react-router-dom, axios.

## Роли

- **Администратор** — полный доступ: справочники (клиенты, сотрудники),
  все задачи, финансовые данные.
- **Сотрудник** — видит только задачи, где указан исполнителем или
  контролёром; может редактировать содержимое своих задач (работы,
  запчасти, расходы/доходы, участие/зарплату, менять этап), но не может
  управлять справочниками клиентов/пользователей и не видит чужие задачи.

## Запуск локально

Настройка окружения (venv, `npm install`) — **разовая операция**. После
неё для обычного запуска нужны только последние команды из каждого блока
ниже (`uvicorn` и `npm run dev`) — переустанавливать зависимости или
пересоздавать venv каждый раз не нужно, и БД между запусками не
теряется (см. «Где хранятся данные» ниже).

### Backend

Первая настройка (один раз):

```powershell
cd backend
python -m venv venv
./venv/Scripts/pip install -r requirements.txt
./venv/Scripts/python -m alembic upgrade head
./venv/Scripts/python seed.py   # создаёт этапы задач и администратора; безопасно запускать повторно — уже существующие данные не трогает
```

Обычный запуск (каждый раз):

```powershell
cd backend
./venv/Scripts/python -m uvicorn app.main:app --port 8001
```

Seed создаёт администратора `admin` / `admin123` — **смените пароль после
первого входа** (раздел «Сотрудники» → редактировать).

> Порт 8001 выбран потому, что на этой машине порт 8000 уже занят другим
> вашим проектом (`StudioProjects\STO`). Если он у вас свободен, можно
> использовать 8000 — тогда поправьте `target` в `frontend/vite.config.ts`.

Скопируйте `backend/.env.example` в `backend/.env`, если нужно поменять
`DATABASE_URL`, `SECRET_KEY` или список `CORS_ORIGINS`.

После обновления кода (`git pull` и т.п.) может понадобиться повторно
выполнить `./venv/Scripts/pip install -r requirements.txt` (если
изменились зависимости) и `./venv/Scripts/python -m alembic upgrade head`
(если добавились миграции) — это тоже не требует пересоздания venv или БД.

#### Где хранятся данные

По умолчанию `DATABASE_URL` — это SQLite-файл `backend/crm.db` по
**абсолютному** пути (собирается в `app/core/config.py` от расположения
самого файла конфига, а не от текущей рабочей директории процесса) —
поэтому он всегда один и тот же независимо от того, откуда именно
запущен `uvicorn`, и не пересоздаётся при перезапуске. Если файла нет —
он будет создан заново пустым (например, при самом первом запуске, или
если вы вручную его удалили) — в этом случае нужно заново прогнать
`alembic upgrade head` и `seed.py`.

### Frontend

```powershell
cd frontend
npm install
npm run dev
```

(`npm install` — тоже разовая операция, кроме случаев, когда меняются
зависимости в `package.json`.)

Откройте адрес, который выведет Vite (обычно http://localhost:5173).
Дев-сервер проксирует запросы `/api/*` на backend (`http://127.0.0.1:8001`,
см. `vite.config.ts`) — благодаря этому фронтенд всегда обращается к
одному и тому же относительному пути `/api`, что упрощает будущий перенос
на удалённый сервер (там `/api` будет проксироваться тем же nginx/Caddy, что
раздаёт собранный фронтенд).

> Если после правок код в браузере выглядит «сломанным» или не
> обновляется — скорее всего, открытая вкладка браузера подключена к
> старому/зависшему процессу `npm run dev`, а не к текущему. Остановите
> все запущенные `npm run dev` (Ctrl+C в каждом терминале, где он мог
> остаться висеть) и запустите заново один — Vite обычно сам
> перезагружает страницу через HMR, но если процессов несколько или один
> из них «подвис», вкладка может держать соединение со старым.

## Перенос на удалённый сервер (позже)

Код к этому уже готов, специальных действий из этого MVP не требуется —
на момент переноса нужно будет:

1. Поднять PostgreSQL и указать его в `DATABASE_URL`.
2. Прогнать `alembic upgrade head` на новой БД.
3. Собрать фронтенд (`npm run build` → папка `frontend/dist`) и отдавать
   статику через nginx/Caddy, проксируя `/api/*` на backend-процесс
   (uvicorn/gunicorn).
4. Задать нормальный `SECRET_KEY` и `CORS_ORIGINS` в `.env`.
5. Поставить процесс-менеджер (systemd/docker) — на этом этапе можно будет
   добавить и докеризацию, она сознательно не делалась в MVP.

## Структура

```
backend/
  app/
    core/        # конфиг, БД, JWT/хеширование паролей, зависимости доступа
    models/      # SQLAlchemy-модели
    schemas/     # Pydantic-схемы запросов/ответов
    routers/     # FastAPI-роуты (auth, users, clients, tasks, calendar, catalog, settings, ...)
    services/    # бизнес-логика: расчёт прибыли/зарплаты, конфликты в календаре
  alembic/       # миграции БД
  seed.py        # начальные данные (этапы задач + администратор)
frontend/
  src/
    api/         # axios-клиент и типы запросов к backend
    components/  # переиспользуемые UI-компоненты (Layout, StageSelect, ...)
    context/     # AuthContext (JWT в localStorage)
    pages/       # страницы: логин, задачи, задача, календарь, клиенты, сотрудники
```

## Решения, принятые по ходу разработки

- **Этапы задач** — не жёстко зашитый enum, а таблица-справочник
  (`task_stages`) с полем `order`, чтобы список этапов можно было расширить
  позже без изменения кода (сейчас там 5 стандартных: Новая →
  Согласование → В работе → Готова → Закрыта/Оплачена).
- **Смена этапа** — выпадающий список (в списке задач и в карточке задачи).
  Drag-and-drop канбан на этом стеке потребовал бы существенно больше
  кода ради UX-выигрыша, не критичного для MVP; список выбран как более
  простой в реализации вариант.
- **Зарплата по задаче** (`participations`):
  - почасовые сотрудники — часы подставляются автоматически (сумма
    длительности их «Работ» в задаче), сумма = часы × ставка, оба значения
    можно вручную скорректировать перед сохранением;
  - сотрудники с фиксированной ставкой — сумма вводится вручную при
    добавлении участия в задачу.
  - Сохранённая сумма после этого не пересчитывается автоматически при
    изменении ставки сотрудника или работ задним числом — это осознанно,
    чтобы история начислений по закрытым задачам не «плыла».
- **Конфликты в календаре** — создание пересекающихся по времени работ у
  одного сотрудника не блокируется, но такие работы подсвечиваются в
  календаре бейджем «конфликт» (проверяется по всему расписанию
  сотрудника, а не только в пределах видимого диапазона дат).
- **Финансы по задаче** считаются на бэкенде и отдаются в ответе
  `GET /api/tasks/{id}` тремя полями:
  - `invoice_total` («К оплате») — стоимость работ (услуг) + продажная
    сумма запчастей (кол-во × цена продажи). Это то, что нужно выставить
    клиенту, независимо от того, сколько уже оплачено.
  - `debt` («Задолженность») = `invoice_total` − сумма записей в разделе
    «Оплаты» (может быть отрицательной при переплате).
  - `profit` («Прибыль») = стоимость работ + маржа по запчастям (цена
    продажи − цена закупки) × количество − расходы − начисленные
    зарплаты. Оплаты клиента в прибыль не входят — это лишь погашение
    выставленной суммы, а не отдельная статья дохода.
  Раздел «Оплаты» (бывшие «Доходы») фиксирует только фактически
  полученные от клиента деньги — используется исключительно для расчёта
  задолженности.
- **Справочники услуг и запчастей** (`/catalog`, только администратор) —
  иерархические (произвольная вложенность категорий), у каждой позиции
  можно задать цену по умолчанию. При добавлении работы/запчасти в задачу
  можно выбрать позицию из справочника — название и цена подставятся
  автоматически, но остаются редактируемыми под конкретный случай;
  сохранённые в задаче значения не меняются задним числом при правке
  справочника. Позицию с вложенными нельзя удалить, пока не удалены
  вложенные.
- **Настройки** (`/settings`, доступны всем):
  - тема оформления (светлая/тёмная/как в системе) — личная, хранится в
    `localStorage` браузера;
  - валюта учёта — общая на всю систему, меняется администратором,
    используется для форматирования всех сумм в интерфейсе.
- **Даты и время сериализуются с явным UTC-суффиксом** (`UtcDateTime` в
  `app/schemas/common.py`). В БД все datetime хранятся наивными в UTC (см.
  `to_naive_utc`); если отдавать такое значение в JSON как есть, браузер
  парсит ISO-строку без смещения как **локальное** время, а не UTC — из-за
  этого при просмотре не в UTC+0 время работы визуально «уезжало» на
  величину локального смещения (например, 04:15 по местному вводилось,
  а отображалось как 23:15 предыдущего дня). `UtcDateTime` всегда
  добавляет `+00:00`, поэтому браузер конвертирует в локальное время
  корректно. Применяется во всех datetime-полях, отдаваемых наружу
  (задачи, работы, клиенты, пользователи, календарь).
- **Создание задачи прямо из календаря** — админ выделяет мышью
  промежуток времени в свободной ячейке дня (или просто кликает — тогда
  подставляется час по умолчанию), открывается окно создания задачи
  (клиент, название, описание первой работы) с уже подставленным
  временем начала/окончания работы; после создания — переход в карточку
  новой задачи. Сотрудникам это действие недоступно (создание задач —
  только для администратора, как и обычная кнопка «Новая задача»).
- **Путь к SQLite-файлу и `.env`** резолвятся абсолютно, от расположения
  `app/core/config.py`, а не от текущей рабочей директории процесса —
  иначе запуск `uvicorn`/`alembic` не из `backend/` тихо создал бы новую
  пустую БД в другом месте вместо использования существующей, что
  выглядело бы как «данные пропали».
- **Календарь** — сетка «дни недели × время» (как в Google Calendar): по
  горизонтали дни выбранной недели, по вертикали — шкала времени
  (диапазон часов подстраивается под данные недели), задачи/работы
  отображаются блоками на своём месте по времени. Пересекающиеся по
  времени работы одного сотрудника показываются рядом друг с другом и
  обводятся оранжевым. Клик по блоку открывает карточку задачи.
